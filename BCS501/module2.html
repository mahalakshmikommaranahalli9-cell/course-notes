2. Requirements Engineering

What is a Requirement?

A requirement is a description of a service, function, constraint or capability expected from a software system.

In simple words:

Requirement = What the customer expects the software to do.

What is Requirements Engineering?

Requirements Engineering (RE) is a systematic process of discovering, documenting, analyzing, negotiating and validating the requirements of a software system.

Discover Needs
→
Analyze
→
Document
→
Validate

Why is Requirements Engineering Important?

  • It helps understand what the customer actually needs.
  • It reduces misunderstanding between customer and development team.
  • It provides a foundation for design and implementation.
  • It helps estimate project cost and effort.
  • It provides a basis for testing.
  • It reduces expensive changes later in development.

Functional Requirements

Functional requirements describe what the system should do.

Examples:

  • The system shall allow a student to log in.
  • The system shall generate a marks report.
  • The system shall allow an administrator to add students.

Non-functional Requirements

Non-functional requirements describe constraints and quality characteristics of the system.

Examples:

  • Performance
  • Security
  • Reliability
  • Usability
  • Availability
  • Maintainability
Functional Requirement Non-functional Requirement
Describes system functions. Describes qualities and constraints.
Example: Login. Example: Login must complete within a specified response time.
Focuses on what the system does. Focuses on how well the system performs.

3. Establishing the Groundwork

Before detailed requirements are collected, the development team must establish a foundation for communication and understanding.

Main Activities

  1. Identify stakeholders: Identify customers, users, managers, administrators and other people affected by the system.
  2. Recognize multiple viewpoints: Different stakeholders may have different expectations.
  3. Work toward collaboration: Developers and stakeholders should communicate continuously.
  4. Ask initial questions: Understand the problem, objectives, users and constraints.
  5. Define the scope: Clearly identify what is included and excluded from the system.
Stakeholders
→
Problem
→
Objectives
→
Scope
→
Agreement

Example — College Management System

Possible stakeholders are:

  • Students
  • Faculty
  • Principal
  • Department staff
  • Parents
  • System administrator

Each stakeholder can provide different requirements. For example, students may need attendance viewing while administrators may need student record management.

4. Eliciting Requirements

Requirements elicitation is the process of collecting requirements from stakeholders and other sources.

Common Elicitation Techniques

Technique Description
Interviews Direct discussion with stakeholders.
Questionnaires Collect information from many users using structured questions.
Observation Observe users performing their real work.
Workshops Group discussions involving stakeholders and developers.
Document analysis Study existing documents, forms and reports.
Prototyping Create an early version to understand unclear requirements.

Basic Elicitation Process

→

→
Organize
→
Prioritize
→
Document
Exam Point: Requirement elicitation is difficult because stakeholders may not know exactly what they need, different stakeholders may disagree, and requirements may change during development.

5. Developing Use Cases

What is a Use Case?

A use case describes how an actor interacts with a software system to achieve a particular goal.

Important Terms

  • Actor: A person, organization or external system that interacts with the system.
  • Use Case: A function or goal provided by the system.
  • System Boundary: Defines what belongs to the system.
  • Association: Relationship between an actor and a use case.

Example — Home Security System

HOME SECURITY SYSTEM
👤
Home Owner

Arm System
Disarm System
View Camera

Detect Intrusion
Send Alert

Steps for Developing an Effective Use Case

  1. Identify the actors.
  2. Identify the goals of each actor.
  3. Identify the use cases that satisfy those goals.
  4. Define the normal flow of events.
  5. Identify alternative flows.
  6. Identify exceptions.
  7. Review the use case with stakeholders.

Example Use Case Description

Item Example
Use Case Student Login
Actor Student
Goal Access student dashboard
Precondition Student has a registered account
Main Flow Enter username → Enter password → Validate → Display dashboard
Alternative Flow Incorrect password → Display error

6. Building the Requirements Model

A requirements model represents the requirements of a system using different modeling techniques.

The model helps developers understand the system before design and coding.

Major Views of a Requirements Model

Class / Information View
→
Flow View

Why Build a Requirements Model?

  • Provides a visual representation of requirements.
  • Improves communication.
  • Helps discover missing requirements.
  • Helps identify inconsistencies.
  • Provides a foundation for design.
  • Helps stakeholders verify their needs.

Requirements Analysis

Requirements analysis examines collected requirements to identify relationships, conflicts, missing information and feasibility.

Remember: Elicitation collects requirements; analysis examines and organizes them.

7. Negotiating Requirements

Different stakeholders may request different features, and some requirements may conflict with one another. Requirements negotiation is used to reach an acceptable agreement.

Why is Negotiation Required?

  • Different stakeholders have different priorities.
  • Resources are limited.
  • Time and budget may be limited.
  • Some requirements may conflict.
  • Some requested features may not be technically feasible.

Negotiation Process

Identify Conflicts
→
Discuss Priorities
→
Evaluate Alternatives
→
Reach Agreement
→
Document

Example

Suppose a student portal stakeholder requests ten advanced features but the project has limited time.

The team and stakeholders can classify requirements as:

  • Must have
  • Should have
  • Could have
  • Can be postponed

8. Validating Requirements

Requirements validation checks whether the documented requirements correctly represent what the stakeholders actually need.

Validation Checks

Check Meaning
Validity Does the requirement represent a real stakeholder need?
Consistency Do requirements conflict with each other?
Completeness Are all required functions and constraints included?
Realism Can the requirement actually be implemented with available resources?
Verifiability Can the requirement be tested or checked?

Example

Bad requirement:

"The system should be very fast."

This is difficult to verify because "very fast" is not measurable.

Better requirement:

"The system shall display the student dashboard within the specified response time under the defined operating conditions."

Requirements Review

Requirements can be reviewed by developers, customers, testers and other stakeholders to identify defects before development begins.

9. Scenario-Based Modeling

Scenario-based modeling describes how users interact with the system. The use case is a major technique used for representing scenario-based requirements.

Scenario

A scenario describes a specific sequence of activities that occurs when an actor interacts with the system.

Example — ATM Withdrawal

  1. Customer inserts card.
  2. ATM asks for PIN.
  3. Customer enters PIN.
  4. System validates PIN.
  5. Customer selects withdrawal.
  6. Customer enters amount.
  7. System checks balance.
  8. ATM dispenses cash.
  9. Transaction is recorded.
Insert Card
→
Enter PIN
→
Select Withdrawal
→
Enter Amount
→
Receive Cash

Benefits

  • Easy for users to understand.
  • Shows interaction between actor and system.
  • Helps identify missing functionality.
  • Provides input for further modeling.

10. UML Models that Supplement the Use Case

UML stands for Unified Modeling Language. It provides standard diagrams for representing different aspects of a software system.

Useful UML Models

Model / Diagram Purpose
Use Case Diagram Shows actors and system functions.
Activity Diagram Shows workflow or sequence of activities.
Class Diagram Shows classes, attributes, operations and relationships.
Sequence Diagram Shows interaction between objects over time.
State Diagram Shows states and transitions of an object/system.

11. Data Modeling Concepts

Data modeling represents the information that a software system must manage. It helps identify important data objects and their relationships.

Basic Concepts

  • Entity: A meaningful object about which information is stored.
  • Attribute: A property of an entity.
  • Relationship: Association between entities.

Example — College System

Entity Possible Attributes
Student Student ID, Name, Email, Semester
Course Course Code, Course Name, Credits
Faculty Faculty ID, Name, Department

12. Class-Based Modeling

Class-based modeling identifies classes and describes their attributes, operations and relationships.

Class

A class represents a collection of objects having common characteristics and behavior.

Example — Student Class

Student

Attributes

  • studentId
  • name
  • email

Operations

  • login()
  • viewMarks()
  • viewAttendance()

Analysis Classes

Analysis classes are classes identified during requirements analysis to represent important concepts in the problem domain.

Common categories include:

  • Entity classes: Represent information or business data.
  • Boundary classes: Represent interaction with users or external systems.
  • Control classes: Coordinate processing or system behavior.

14. Quality Function Deployment — QFD

Quality Function Deployment (QFD) is a technique used to translate customer needs into technical requirements.

Basic Idea

Customer Needs
→
Prioritize Needs
→
Technical Requirements
→
Product / System

Three Types of QFD

Type Purpose
Normal QFD Identifies customer requirements and translates them into technical characteristics.
QFD for Product Design Focuses on translating customer requirements into product design features.
QFD for Manufacturing Helps translate design requirements into manufacturing requirements.

16. Behavioral Modeling

Behavioral modeling describes how the system or its components respond to events over time.

Important Concepts

  • Event: Something that causes a response.
  • State: A condition in which an object/system exists.
  • Transition: Movement from one state to another.
  • Action: Activity performed as a response.

Example — ATM Card

Card Inserted
→
PIN Verification
→
Authenticated
→
Transaction
→
Card Returned

Behavioral Model Helps Answer

  • What happens when an event occurs?
  • What state is the system currently in?
  • What transition should occur?
  • What action should be performed?

17. Requirements Modeling — Quick Comparison

Model Main Focus Example

Scenario = WHO does WHAT
Class = WHAT objects exist

19. 2-Mark Questions & Answers

1. What is Requirements Engineering?

Requirements Engineering is the systematic process of discovering, analyzing, documenting, negotiating and validating software requirements.

2. What is requirement elicitation?

It is the process of collecting requirements from customers, users and other stakeholders.

3. What is a use case?

A use case describes an interaction between an actor and a system to achieve a particular goal.

4. What is an actor?

An actor is a person, organization or external system that interacts with the software system.

5. What is requirements validation?

Requirements validation checks whether documented requirements are correct, complete, consistent, realistic and verifiable.

6. What is CRC?

CRC stands for Class, Responsibility and Collaborator.

7. What is QFD?

QFD stands for Quality Function Deployment. It translates customer needs into technical requirements.

8. What is behavioral modeling?

Behavioral modeling represents how a system or object responds to events and changes state over time.
