1. Requirements Engineering

Requirements engineering is a systematic process used to identify, understand, document and validate what stakeholders expect from a software system.

Definition: Requirements engineering is the process of discovering, documenting and maintaining the services and constraints required from a system.

Main Activities

Inception → Elicitation → Elaboration → Negotiation → Specification → Validation

2. Establishing the Groundwork

Before requirements are collected in detail, the development team establishes a foundation for communication with stakeholders.

Important Activities

  1. Identify stakeholders.
  2. Understand the problem and business objectives.
  3. Identify project scope.
  4. Establish communication methods.
  5. Identify constraints and assumptions.
  6. Determine feasibility and project context.

3. Eliciting Requirements

Requirements elicitation is the process of collecting requirements from customers, users and other stakeholders.

Common Elicitation Techniques

  • Interviews
  • Questionnaires
  • Observation
  • Workshops
  • Brainstorming
  • Document analysis
  • Prototyping

4. Developing Use Cases

A use case describes how an actor interacts with a system to accomplish a particular goal.

Example: In an online shopping system, a customer can "Place Order" by selecting products, entering delivery details and confirming payment.

Basic Use Case Elements

  • Actor: external entity interacting with the system.
  • Use Case: functionality provided by the system.
  • System Boundary: identifies what belongs to the system.
  • Association: relationship between actor and use case.

5. Building the Requirements Model

A requirements model represents the requirements from different viewpoints so that developers and stakeholders can understand the proposed system.

Major Modeling Elements

  • Scenario-based elements
  • Class-based elements
  • Behavioral elements
  • Flow-oriented elements
  • Data-oriented elements

6. Quality Function Deployment (QFD)

Quality Function Deployment is a technique used to identify customer requirements and translate them into technical or engineering requirements.

Types of Requirements in QFD

Type Description
Normal Requirements Requirements explicitly requested by customers or users.
Expected Requirements Features that users normally expect even if they do not explicitly state them.
Exciting Requirements Features that provide additional satisfaction when present.

7. Negotiating Requirements

Different stakeholders may have conflicting requirements. Negotiation is used to reach an acceptable agreement.

Basic Steps

  1. Identify conflicting requirements.
  2. Discuss stakeholder priorities.
  3. Identify technical and business constraints.
  4. Find alternative solutions.
  5. Agree on priorities and compromises.
  6. Document the final decisions.

8. Validating Requirements

Requirements validation checks whether documented requirements correctly represent stakeholder needs and are suitable for development.

Validation Checks

  • Validity: Does the requirement represent a real need?
  • Consistency: Are requirements free from conflicts?
  • Completeness: Are all important requirements included?
  • Realism: Can the requirement actually be implemented?
  • Verifiability: Can the requirement be tested?

9. Scenario-Based Modeling

Scenario-based modeling describes system behavior from the viewpoint of users or external actors.

Example

Consider an ATM withdrawal scenario:

  1. Customer inserts the card.
  2. System asks for PIN.
  3. Customer enters PIN.
  4. System validates the PIN.
  5. Customer selects withdrawal.
  6. System provides the requested amount.

UML provides standardized diagrams for representing different views of a software system.

Useful UML Models

12. Class-Responsibility-Collaborator (CRC) Modeling

CRC modeling is a technique used to identify classes and distribute responsibilities among them.

Three Components

  • Class: Represents an important entity or abstraction.
  • Responsibility: Describes what the class knows or does.
  • Collaborator: Identifies another class that helps perform a responsibility.

13. Flow-Oriented Modeling

Flow-oriented modeling represents how information moves through a system and how it is transformed by processing functions.

Input → Process → Output

Data Flow Diagrams (DFDs) are commonly used to represent information flow.

14. Behavioral Modeling

Behavioral modeling describes how a system or object responds to events and how its state changes.

Event → State Change → Action

State diagrams are commonly used to represent behavioral aspects of a system.

⭐ Important VTU Questions

Q1. With an example, describe CRC modeling.

Answer:

CRC stands for Class-Responsibility-Collaborator. It is a technique used during object-oriented requirements modeling.

A CRC card identifies a class, the responsibilities assigned to it, and the other classes that collaborate with it.

For example, in a college system, the Student class may have responsibilities such as registering for courses and viewing marks. Its collaborators may include Course and Faculty.

Q2. Explain the three types of QFD requirements with examples.

Answer:
  • Normal requirements: Explicitly requested features. Example: user login.
  • Expected requirements: Features users normally expect. Example: reasonable response time.
  • Exciting requirements: Additional features that can increase user satisfaction. Example: personalized recommendations.

Q3. Explain scenario-based modeling with an example.

Answer:

Scenario-based modeling describes the interaction between an external actor and a software system.

For example, an ATM withdrawal scenario includes inserting a card, entering a PIN, selecting withdrawal, validating the transaction and dispensing cash.

Q4. How can you develop an effective use case?

Answer:
  1. Identify the primary actor.
  2. Identify the actor's goal.
  3. Define the normal flow of events.
  4. Identify alternate and exceptional flows.
  5. Specify preconditions.
  6. Specify postconditions.
  7. Review the use case with stakeholders.

Q5. Explain requirements engineering and its major activities.

Answer:

Requirements engineering is the systematic process of discovering, documenting, negotiating and validating system requirements.

  1. Inception
  2. Elicitation
  3. Elaboration
  4. Negotiation
  5. Specification
  6. Validation

Q6. Explain requirements validation.

Answer:

Requirements validation ensures that the documented requirements correctly describe the required system.

The main checks are validity, consistency, completeness, realism and verifiability.

Q7. Explain class-based modeling.

Answer:

Class-based modeling identifies classes, attributes, operations and relationships among objects in the problem domain.

For example, in a college system, Student, Course and Faculty can be identified as analysis classes.

Q8. Explain flow-oriented modeling.

Answer:

Flow-oriented modeling represents the movement and transformation of information within a system.

A Data Flow Diagram can represent external entities, processes, data stores and data flows.

Q9. Explain behavioral modeling.

Answer:

Behavioral modeling represents how a system responds to events and how its state changes. State diagrams are commonly used to model such behavior.
