📚 Module 5 — Software Quality & Estimation

Software quality and project estimation are two important parts of software project management.

Software quality focuses on whether the software satisfies specified requirements and expected quality characteristics.

Software estimation attempts to determine the effort, time, cost and resources required to complete a software project.

Easy Memory:

Quality → "Is the software good enough?"
Estimation → "How much effort, time and money will it take?"

1. Software Quality

Software quality refers to the degree to which software satisfies specified requirements and relevant quality characteristics.

Simple Definition: Software quality means developing software that correctly performs its required functions and satisfies expected quality requirements.

Important Quality Characteristics

  • Correctness
  • Reliability
  • Efficiency
  • Usability
  • Maintainability
  • Portability
  • Security
  • Performance

Why is Software Quality Important?

  • Reduces software defects.
  • Improves customer satisfaction.
  • Reduces maintenance cost.
  • Improves reliability.
  • Improves maintainability.
  • Reduces project risks.
  • Improves product reputation.

2. Place of Software Quality in Project Management

Quality is not a separate activity performed only at the end of a project. It should be considered throughout planning, development, testing and deployment.

PROJECT MANAGEMENT │ ┌─────────────┼─────────────┐ ↓ ↓ ↓ PLANNING DEVELOPMENT CONTROL │ │ │ ↓ ↓ ↓ QUALITY QUALITY QUALITY PLANNING ASSURANCE CONTROL │ │ │ └─────────────┼─────────────┘ ↓ QUALITY PRODUCT

Quality Activities

  1. Define quality requirements.
  2. Prepare quality plans.
  3. Define standards and procedures.
  4. Perform reviews.
  5. Conduct testing.
  6. Track defects.
  7. Measure quality.
  8. Take corrective action.
Exam Point: Quality management helps ensure that project deliverables meet defined requirements while also supporting control of defects, cost, schedule and customer expectations.

3. Software Quality Management

Software Quality Management is the set of activities used to plan, assure and control the quality of software and software-development processes.

Main Components

1. Quality Planning

Identifies quality standards, objectives, measurements and procedures that will be used in the project.

2. Quality Assurance

Focuses on processes and activities used to provide confidence that quality requirements will be satisfied.

3. Quality Control

Focuses on examining actual work products and identifying defects or deviations from requirements.

QUALITY MANAGEMENT │ ┌───────┼────────┐ ↓ ↓ ↓ Planning Assurance Control │ │ │ ↓ ↓ ↓ Standards Processes Products │ │ │ └───────┼────────┘ ↓ Quality Result

4. Software Quality Models

A software quality model provides a structured way to describe and evaluate quality characteristics of software.

Why Use Quality Models?

  • Identify important quality characteristics.
  • Provide measurable quality attributes.
  • Help compare software products.
  • Support quality evaluation.
  • Help identify areas for improvement.

Common Quality Models / Frameworks

Model Main Idea
McCall's Model Groups software quality factors into major quality perspectives.
ISO/IEC 9126 Provides a structured quality model for software product evaluation.
ISO/IEC 25010 Provides a modern software product quality model.
CMM / CMMI Focuses strongly on process maturity and organizational process improvement.

5. McCall's Quality Model

McCall's quality model organizes software quality factors into three broad perspectives:

McCALL QUALITY MODEL │ ┌──────────────┼──────────────┐ ↓ ↓ ↓ PRODUCT PRODUCT PRODUCT REVISION TRANSITION OPERATION │ │ │ ↓ ↓ ↓ Maintainability Flexibility Correctness Flexibility Testability Reliability Testability Portability Efficiency Integrity Usability

1. Product Operation

Concerns how well the software operates during use.

  • Correctness
  • Reliability
  • Efficiency
  • Integrity
  • Usability

2. Product Revision

Concerns how easily software can be modified.

  • Maintainability
  • Flexibility
  • Testability

3. Product Transition

Concerns adapting or moving software to other environments.

  • Portability
  • Reusability
  • Interoperability

6. ISO-Based Quality View

ISO quality models provide structured characteristics that can be used to evaluate software quality.

Important Product Quality Characteristics

  • Functionality
  • Reliability
  • Usability
  • Efficiency
  • Maintainability
  • Portability
Memory Trick:

F R U E M P
Functionality → Reliability → Usability → Efficiency → Maintainability → Portability

7. Product vs Process Quality Management

Product Quality Management Process Quality Management
Focuses on the quality of the software product. Focuses on the quality of the development process.
Examines features and behavior of the final product. Examines whether defined processes are followed.
Uses testing and product measurements. Uses process audits, reviews and process metrics.
Main concern is product characteristics. Main concern is process effectiveness and consistency.
Example: reliability testing. Example: checking whether required review procedures were followed.

8. Software Project Estimation

Software project estimation is the process of predicting the effort, cost, duration and resources required to complete a software project.

Estimate:

How much software must be developed?
How much effort is required?
How much will it cost?
How long will it take?

Major Estimation Parameters

  • Software size
  • Effort
  • Development time
  • Cost
  • Resources
  • Team size
REQUIREMENTS ↓ ESTIMATE SIZE ↓ ESTIMATE EFFORT ↓ ESTIMATE COST ↓ ESTIMATE SCHEDULE ↓ ALLOCATE RESOURCES

9. Decomposition Techniques

Decomposition breaks a large software project into smaller parts so that each part can be estimated more easily.

Why Decompose?

  • Large systems are difficult to estimate directly.
  • Smaller components are easier to understand.
  • Different components may have different complexity.
  • Estimates can be combined to obtain an overall estimate.

Basic Decomposition Process

SOFTWARE PROJECT ↓ ┌──────────┼──────────┐ ↓ ↓ ↓ Module A Module B Module C ↓ ↓ ↓ Estimate Estimate Estimate │ │ │ └──────────┼──────────┘ ↓ Total Estimate

Two Important Decomposition Approaches

1. Problem-Based Decomposition

The project is decomposed according to the functions or features that must be implemented.

2. Process-Based Decomposition

The project is decomposed according to the activities required to perform the software process.

10. Size-Oriented Estimation

Size-oriented estimation uses software size as an important basis for estimating effort, cost and productivity.

LOC

LOC (Lines of Code) represents the number of source-code lines used to implement a software system.

Example

Suppose a project is estimated to contain 10,000 lines of code.

If historical data provides effort per thousand lines, that information can be used to estimate total effort.

Limitation: LOC is language-dependent and is difficult to estimate accurately before design and implementation.

11. LOC-Based Estimation

LOC-based estimation uses estimated lines of code to derive effort or productivity values.

Common Measures

Productivity:
LOC / Person-Month

Defect Density:
Defects / KLOC

Cost per KLOC:
Total Cost / KLOC

Advantages

  • Easy to understand.
  • Useful when historical LOC data exists.
  • Can support productivity calculations.

Limitations

  • Difficult to estimate LOC early.
  • Depends on programming language.
  • Encourages focus on code quantity.
  • Different coding styles produce different LOC.

12. Function Point Estimation

Function Point Analysis estimates software size based on the functionality provided to users rather than directly counting lines of source code.

Five Major Function Types

Function Type Meaning
External Inputs (EI) Data entering the system.
External Outputs (EO) Information produced by the system.
External Inquiries (EQ) Input-output interactions that provide information.
Internal Logical Files (ILF) Logical groups of data maintained by the system.
External Interface Files (EIF) Data used by the system but maintained outside it.
FUNCTION POINTS │ ┌────────────┼────────────┐ ↓ ↓ ↓ EI EO EQ │ │ │ └────────────┼────────────┘ ↓ ILF + EIF ↓ FUNCTIONAL SIZE

Advantages

  • Less dependent on programming language.
  • Focuses on user-visible functionality.
  • Can be useful during early planning.

13. Empirical Estimation Models

An empirical estimation model uses mathematical equations derived from observations and historical project data.

Simple Idea: Past project data → Mathematical relationship → Estimate for a new project

General Form

Effort = a × (Size)b

where a and b are model parameters determined from historical data.

Examples

  • COCOMO
  • Putnam-based approaches
  • Other regression-based estimation models

Advantages

  • Uses historical evidence.
  • Provides systematic estimates.
  • Can be automated.

Limitations

  • Accuracy depends on historical data.
  • Different organizations may require different parameters.
  • New technology may not match old project data.
  • Wrong size estimates produce wrong effort estimates.

14. COCOMO Model

COCOMO stands for Constructive Cost Model. It is an empirical software estimation model associated with Barry Boehm.

Basic COCOMO Effort Equation

Effort = a × (KLOC)b

Effort is commonly expressed in person-months.

Development Time

Development Time = c × (Effort)d

Traditional COCOMO Project Modes

Mode General Description
Organic Relatively small and familiar projects with experienced teams.
Semi-detached Projects with intermediate complexity and mixed experience.
Embedded Projects with strong hardware, software, regulatory or operational constraints.

COCOMO Estimation Flow

Estimate KLOC ↓ Select Project Mode ↓ Apply COCOMO Formula ↓ Estimate Effort ↓ Estimate Development Time ↓ Estimate Staffing / Cost
Exam Tip: Remember:

KLOC → Effort → Development Time → Cost

15. Observations on Project Estimation

Software estimation is difficult because software projects involve uncertainty, changing requirements, people, technology and varying levels of complexity.

Important Observations

  1. Estimation is uncertain: Early estimates may change as more information becomes available.
  2. Requirements affect estimates: Unclear or changing requirements make estimation harder.
  3. Historical data is valuable: Past project information can improve future estimates.
  4. Different projects differ: A model suitable for one project may not give the same accuracy for another.
  5. Size estimation is important: Incorrect size estimates can affect effort and cost.
  6. Risk affects estimation: Technical and organizational risks may increase effort and schedule.
  7. Estimates should be revised: Estimates can be refined as project knowledge improves.
  8. Multiple estimation approaches help: Using more than one technique can provide useful cross-checking.
INITIAL ESTIMATE ↓ PROJECT STARTS ↓ MORE INFORMATION ↓ REVISE ESTIMATE ↓ BETTER ESTIMATE ↓ PROJECT CONTROL

17. ✍️ 2-Mark Questions & Answers

1. Define Software Quality.
Software quality is the degree to which software satisfies specified requirements and expected quality characteristics.
2. What is Software Quality Management?
It is the set of activities used to plan, assure and control the quality of software and its development processes.
3. What is Software Estimation?
Software estimation is the process of predicting the effort, cost, duration and resources required for a software project.
4. What is decomposition?
Decomposition is the process of dividing a large software project into smaller components for easier estimation.
5. What is LOC?
LOC stands for Lines of Code and represents the amount of source code in a software system.
6. What is KLOC?
KLOC means Thousand Lines of Code and is commonly used as a software size measure.
7. What is Function Point?
Function Point is a measure of software size based on the functionality provided to users.
8. What is an empirical estimation model?
It is an estimation model based on mathematical relationships derived from observations and historical project data.
9. What is COCOMO?
COCOMO stands for Constructive Cost Model. It is an empirical model used to estimate software development effort and time.
10. What is quality assurance?
Quality assurance consists of planned activities used to provide confidence that software processes and products will satisfy quality requirements.
